## The findings, with enough to decide

### 1 — The API paths are unversioned → DO (PR C)

Every controller maps `/api`, never `/api/v1` (`MirrorController:15`,
`SyncController:22`, `AuditController:35`, and the rest).
`compatibility.md:225-230` admits it and defers the version segment to "the
change that introduces API versioning".

**Why DO:** the contract's own remedy for a future break is "move the prefix and
ship a major". With no `v1`, the first break gives `/api/v2/…` beside a bare
`/api/…` that must be supported forever. Renaming now is free.

### 2 — The documented error body is not the one sent → DO (PR D)

`api/index.md:112` promises RFC 7807 `ProblemDetail`. But ~35 refusals throw
`ResponseStatusException`, and there is **no `@ControllerAdvice` in the tree and
no `problemdetails` setting** — so Boot renders those as
`{timestamp,status,error,path}` with the reason text **dropped**. The portal reads
`body.detail` and silently falls back to `"409 Conflict"`. No test asserts on any
error body. `openapi.json` then documents ~90 4xx responses with the *success*
schema.

**Why DO:** the wire shape of every error is a contract field set, so it freezes.
One line of config fixes the runtime half.

### 3 — `GET /api/audit` returns the whole ledger untyped → DO (PR E)

`AdminController:606` returns `List<Map<String,Object>>` from
`SELECT * FROM fetch_log ORDER BY id` (`FetchLogRepository:104`) — no limit, no
cursor, raw column names as JSON keys. The portal audit page calls it. Its own
description claims "Portal actions are not in this ledger", contradicted by
`AdminAuditLogger:34` writing `source = "admin"` rows there.

**Why DO:** array → paginated envelope is a break later, and every column rename
becomes an API break because the schema *is* the payload. Also: the in-flight
`bound-ledger-growth` change calls `fetch_log` the table that ends the
deployment — this read ends the portal first.

### 4 — The chart corrupts storage and restarts healthy pods → DO (PR F)

Three things in `helm/skills-gateway/templates/deployment.yaml`: no `strategy`, so
the default `RollingUpdate` overlaps two pods on one volume — which
`deploying-without-kubernetes.md:237` says corrupts repositories; liveness *and*
readiness both probe `/actuator/health`, which aggregates the DataSource and
object-store indicators, so a PostgreSQL or S3 outage restarts pods that are
fine; and no `server.shutdown: graceful`, so an in-flight `upload-pack` is cut on
SIGTERM.

**Why DO:** data corruption on every `helm upgrade`, and the fix is about ten
lines. This is also a gate on publishing the review.

### 5 — No backup, restore or upgrade procedure → DO (PR F)

The only `pg_dump` in the whole docs site is in `leaving-the-gateway.md` — an
*exit* guide. There is no upgrade page. `deploying-without-kubernetes.md:232`
states the hazard precisely ("the volume and the database are one estate") and
then says nothing about taking a consistent copy of both, or restoring one.
Bucket versioning is recorded as unverified, so the object store's own
point-in-time tooling is out too.

**Why DO:** 1.0.0 is where `V1` freezes and the migration chain begins, so upgrade
order starts mattering on the first patch — and it is the version people deploy
for real. Restoring the database from Monday and `/data` from Tuesday is a
split-brain the gateway cannot detect. The fix is one operations page.

### 6 — A marketplace can never be corrected or removed → DEFER to an issue

No `DELETE` or `PUT` for marketplaces exists; the estate reconciler is
additive-only; `url` has no setter. A typo'd URL or a moved upstream leaves a
permanent dead row that the sync sweep keeps stamping.

**Why DEFER, against the review's should-fix:** nothing here is actually
expensive after the freeze. Soft-retire never deletes, so the missing `ON DELETE`
on `snapshots.marketplace_id` never fires, and `deleted_at` is an additive
nullable column — the cheapest migration there is. File the issue and record
soft-retire as the intended shape so the choice is not reopened later.

### 7 — `webhook_deliveries` grows without bound → DO, folded into `bound-ledger-growth`

Every delivery stores its full `payload TEXT` (`V1__init.sql:317`), and there is
no `DELETE FROM webhook_deliveries` anywhere. The listing is capped at 500; the
table is not.

**Why fold rather than its own PR:** it is the same compaction pass and the same
unbounded-table argument as the change already in flight. A second change
touching one method is waste. If it is excluded instead, that change's design
must say why.

### 8a — `vetting_runs.trigger` is TEXT holding a closed set → DO (PR A)

`V1__init.sql:369`. The API already exposes the three values as an enum
(`ingestion` / `revet-scheduled` / `revet-manual`), and `V1`'s own header states
the policy this violates.

**Why DO:** one line now, a migration forever.

### 8b — `marketplaces.name` has no `CHECK` constraint → DO (PR A)

`V1__init.sql:42` has no pattern constraint. Meanwhile `access_tokens.scopes`
(`:252`) is comma-delimited **because** "names cannot contain the delimiter".

**Why DO:** the token scoping depends on an assumption the schema does not
enforce. One line.

### 8c — No index on `access_tokens (principal)` → DO (PR A)

`TokenRepository:126` filters on `principal` for every token listing.

**Why DO:** one line, and index changes after the freeze are migrations.

### 8d — Comma-delimited TEXT should be `TEXT[]` → DO (PR A)

`scopes`, `push_scopes`, `api_scopes` and `webhook_subscribers.events` are one
opaque string with commas inside (`"acme,widgets"`), split in Java at
`AccessToken:33,63,99`, `WebhookSubscriber:21` and `WebhookService:310`.
`vetting_chain_orders.vetters` (`:602`) is a real array, which is why it can carry
`CHECK (cardinality(vetters) > 0)`.

**Why DO — flipped from WON'T on 2026-09-20.** As inconsistency it was cosmetic,
and 8b's `CHECK` removes the actual hazard of the comma form. What flipped it is a
query the owner wants and the comma form cannot serve: **which tokens can reach
this marketplace.** With `TEXT[]` that is one indexed `'acme' = ANY(scopes)`; with
a delimited string it is a full scan plus a split in Java. After a marketplace is
compromised that is the token-revocation equivalent of the blast-radius query, so
the array stops being a style preference and becomes the enabler.

`TEXT[]` is the project's stated direction for any multi-valued column from here
on — recorded in `.claude/skills/code-conventions/SKILL.md` beside the native-enum
rule, so it is a convention and not a one-off.

Note the two halves: converting the columns belongs in PR A while the schema is
open; **the query itself is a new read and therefore its own OpenSpec change**, not
a free rider on a schema PR.

### 9 — Enum casing is inconsistent inside one document → DO (PR C)

`openapi.json` carries `CLEAR`/`BLOCKED`, `PASS`/`WARN`/`FAIL`, `APPLIED`,
`GLOBAL`/`DEFAULT` beside `held`/`approved`, `admin`/`approver`, `append-only`,
`ingestion`. Every consumer will encode both conventions.

**Why DO:** renaming a value is a break later. Lowercase throughout matches the
PostgreSQL enums. Bundles with 1 because both rewrite `openapi.json`.

### 10 — Metrics can only leave by OTLP, and the chart cannot enable it → DO (PR F)

No `micrometer-registry-prometheus` in `pom.xml`; `application.yaml` exposes only
`health,sbom`; export needs `arconia.otel.enabled=true` plus `OTEL_EXPORTER_OTLP_*`;
`helm/values.yaml` has no otel or prometheus values at all.

**Why DO:** the docs name two metrics to **alert on** —
`storage.conditional_write.exhaustions` and `mirror.stale_refs` — and on a default
chart install they reach nobody. That is a documented promise the deployment
cannot keep.

### 11a — Webhook signing secrets are plaintext at rest, and undocumented → DO (PR B)

`webhook_subscribers.secret` and `marketplaces.webhook_secret`
(`V1__init.sql:67, 308`) are stored as-is. The docs state the PAT posture
("hashed at rest") and say nothing about these.

**Why DO:** the storage is legitimate — HMAC needs a recoverable key — so the
defect is honesty, not design. One paragraph in `concepts/trust-boundaries.md`,
and it is the disclosure gate on publishing this review.

### 11b — Envelope-encrypt the secret columns → WON'T

**Why WON'T:** HMAC needs the key recoverable, and the database is already inside
the trust boundary, so encryption at rest in the same system buys little. An
`enc:` value prefix remains available additively, so no column shape freezes and
nothing is foreclosed. Reconsider if a deployment ever needs the database to be
outside the boundary.

### 12 — `RemovedProperties` refusals expire at the next major, which is 1.0.0 → DO (PR C)

`compatibility.md:148-156` and `config/RemovedProperties.java`. The startup
refusals for `roles.enabled` and `cache.ref-freshness` are promised to go "at the
next major".

**Why DO:** 1.0.0 *is* that major, so shipping them freezes a migration aid into
the supported surface. Delete both and the doc paragraph — or re-date the promise,
which is the weaker option.

### 13 — The capability map under-counts the portal's pages → DO (PR B)

`capability-map.md:33` says "The seven pages …" and lists seven.
`SpaController:10` routes eight, including `/vetting`, which `portal.md:16` lists
as a governance page.

**Why DO:** one line, and the stop rule leans on this map being exact.

## Follow-up scope this run created

- **PR C retired a requirement.** `GW_AUTH_0027 — The removed enforcement property is
  refused rather than ignored` is gone, because its own text scheduled it for removal
  at this major. The whole `RemovedProperties` mechanism went rather than being kept
  with an empty map. reqstool is 247/247, not 248 — the count going down is the change.
  **This is the judgment call in the run most worth reversing if the owner disagrees.**

- **PR A found a fifth delimited column** the review missed:
  `vetting_overrides.blocking_vetters`, plus `uncovered_findings` on the same
  table. Both converted in PR A rather than left to violate the new convention.
- **PR A changed three payloads, not just columns.** The first cut kept the
  published shapes delimited to avoid a contract break; the owner corrected that
  — pre-1.0 there is nothing to be compatible with — so `events`,
  `blockingVetters` and `uncoveredFindings` are arrays and PR A ships as
  `feat(api)!`. The `events` payload item is therefore **done**, not PR C's.
- **`e2e/run-e2e.sh` defaults the gateway to port 8081**, which is React Native
  Metro's default and collides on a machine doing both. Change the default.
- **Enabling a vetter re-runs nothing.** Toggling per-marketplace or globally
  triggers no re-vetting; held snapshots are never re-vetted at all and approval
  gates on the stored latest run, so a snapshot can be approved on evidence a
  newly enabled vetter never produced. Needs its own issue.

- **"Which tokens can reach this marketplace"** — the query that justified the 8d
  flip. It is a new API read on the auth trust boundary, so it is its own OpenSpec
  change with its own requirement and old-coder discipline, **not** part of PR A.
  PR A only makes it possible. Not started, and not in the A–F set.
