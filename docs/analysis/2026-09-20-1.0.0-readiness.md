# 1.0.0 readiness review — 2026-09-20

Reviewed at `c14b255c`. Read-only; nothing built or run. Every claim carries the
file and line that proves it. Findings 1–5 were independently re-verified after
the review; 6–13 are as reported.

**Held until its own findings were fixed, now published.** The repo is public and two
findings described unfixed weaknesses — 11a (webhook signing secrets plaintext at rest,
undocumented) and 4 (the chart corrupts the filesystem backend on upgrade). Same call as
the 2026-09-08 assessment's D1: hold, then publish. 11a shipped in #451 and 4 in #456, so
this is published as of 2026-09-21. **Everything described below as a defect is fixed**
unless its row in the tracker says otherwise — read the tracker for current state, not
this file.

**The lens.** 1.0.0 is where `V1__init.sql` freezes and the API contract becomes
additive-only within the major (`docs/manual/reference/compatibility.md`). Every
finding is ordered by *cost of fixing after that freeze*, not by severity.

## Blocking

### 1. API — the paths are unversioned (API)

`compatibility.md:225-230` states it: "Endpoints are unversioned today
(`/api/marketplaces`, not `/api/v1/marketplaces`). The version segment arrives
with the change that introduces API versioning." Confirmed across controllers —
`MirrorController:15`, `SnapshotPreviewController:30`, `SyncController:22`,
`AuditController:35`, `VettingChainSettingsController:31` all map `/api`.

*Worse after the freeze:* the contract's own remedy for a break is "move the
prefix and ship a major" (`compatibility.md:158-162`). With no `v1`, the first
break yields `/api/v2/…` beside a bare `/api/…` that must live forever.

*Fix:* `/api/v1` on every `@RequestMapping`, plus `/status/v1` if that surface is
covered (`compatibility.md:123` says it is). Regenerate `openapi.json`, update
the SPA base path, ship with `!`.

### 2. API — the documented error body is not the one sent (API)

`docs/manual/reference/api/index.md:112-117` promises RFC 7807 `ProblemDetail`
and uses the URL-scheme rejection as its example. That rejection throws
`ResponseStatusException` (`admin/MarketplaceRegistrationService.java:84-106`),
as do ~35 other refusals (`policy/PolicyRuleService.java:41-92`,
`webhook/WebhookService.java:268-319`,
`sync/InboundWebhookController.java:76-103`,
`vetting/VetterToggleService.java:116-217`). Only `@ExceptionHandler` methods
return `ProblemDetail` (`AdminController.java:611-623`).

**Verified: there is no `@ControllerAdvice` anywhere in `src/main/java`, and no
`problemdetails` setting in `src/main/resources`.** Boot 4.1.1 defaults
`spring.mvc.problemdetails.enabled=false` and `server.error.include-message=never`,
so a `ResponseStatusException` renders as `{timestamp,status,error,path}` **with
the reason text dropped**. The SPA reads only `body.detail`
(`src/main/frontend/src/api/client.ts:33-41`) and falls back to
`"409 " + statusText`. No test asserts on any error body, which is why it went
unnoticed. `openapi.json` then documents ~90 4xx responses with the *success*
schema, and 20 more with no content.

*Worse after the freeze:* the wire shape of every error is a contract field set.

*Fix:* `spring.mvc.problemdetails.enabled: true` (one line), an
`OpenApiCustomizer` pointing every 4xx/5xx at a `ProblemDetail` schema,
regenerate `openapi.json`, and one MockMvc assertion on `$.detail` for a
`ResponseStatusException` path so it stays true.

### 3. API — `GET /api/audit` returns the whole ledger as untyped rows (API)

`AdminController.java:606-608` returns `List<Map<String,Object>>` from
`fetchLogRepository.list()`, which is `SELECT * FROM fetch_log ORDER BY id`
(`persistence/FetchLogRepository.java:104`) — no limit, no cursor, raw column
names as JSON keys (`actor_type`, `token_id`, `credential_kind`). The portal
audit page uses it (`src/main/frontend/src/api/queries.ts:592`). The sibling
`GET /api/audit/export` already has `after`/`limit`
(`audit/AuditController.java:121-122`).

The endpoint's own contract text is also false: "Portal actions are not in this
ledger" (`AdminController.java:603-605`) while `admin/AdminAuditLogger.java:34`
writes `source = "admin"` rows into that table.

*Worse after the freeze:* array → paginated envelope is a break, and every column
rename becomes an API break because the schema *is* the payload.

*Collides with:* the in-flight `bound-ledger-growth` change calls `fetch_log`
"the table that ends the deployment". This read ends the portal first.

*Fix:* a typed row record (the export needs one anyway), `after`/`limit` matching
`/api/audit/export`, corrected description. Additive now, a break later.

### 4. OPS — the chart corrupts the filesystem backend on upgrade, and a
dependency outage becomes a restart loop (OPS)

- `deploying-without-kubernetes.md:237-242` states two overlapping processes on
  one volume corrupt repositories and says "configure your platform for
  stop-then-start". **Verified: `helm/skills-gateway/templates/deployment.yaml`
  sets no `strategy`**, so the default `RollingUpdate` overlaps old and new pod
  on every `helm upgrade` — the documented corruption case. `replicaGate`
  (`_helpers.tpl:131-138`) only checks `replicaCount`.
- **Verified: liveness *and* readiness both probe `/actuator/health`**
  (`deployment.yaml:166-173`), which aggregates the DataSource indicator and
  `GitStorageHealthIndicator` — the object-store variant lists the bucket on
  every poll (`observability/GitStorageHealthIndicator.java:50-66`). A PostgreSQL
  or S3 outage therefore fails *liveness* and kubelet restarts healthy pods. The
  docs tell operators to avoid `/liveness` because the security chain blocks it
  (`deploying-without-kubernetes.md:307-309`, `SecurityConfig.java:308-309`).
- **Verified: no `server.shutdown` in `src/main/resources/application.yaml`**, and
  no `terminationGracePeriodSeconds`. An in-flight `upload-pack` or ingestion
  clone is cut on SIGTERM.

*Fix (~10 lines):* `strategy: {type: Recreate}` when
`storage.backend != object-store`; `management.endpoint.health.probes.enabled=true`,
permit `/actuator/health/**`, liveness on `/liveness` and readiness on
`/readiness` with the DB and storage indicators in the readiness group only;
`server.shutdown: graceful`.

### 5. OPS/DOCS — no backup, restore or upgrade procedure (OPS)

**Verified: the only `pg_dump` in the entire docs site is
`guides/leaving-the-gateway.md:87` — an *exit* guide. There is no upgrade page.**
`deploying-without-kubernetes.md:232-235` states the hazard precisely — "the
volume and the database are one estate: a gateway that restarts onto an empty
`/data` still reports its snapshots as published and can serve none of them" —
and then says nothing about taking a consistent copy of both, or restoring one.
For the object store, `storage-backends.md:67-71` records bucket versioning as
*unverified*, so the store's own point-in-time tooling is out too.

*Worse after the freeze:* 1.0.0 is where `V1` freezes and the migration chain
begins, so upgrade order starts mattering on the first patch — and it is the
version people deploy for real. Restoring PostgreSQL from Monday and `/data` from
Tuesday is a split-brain the gateway cannot detect.

*Fix:* one operations page — quiesce, `pg_dump` plus a copy or snapshot of
`data-dir`/bucket prefix **taken together**, restore in the same pairing,
"migrations run at startup, upgrade with one replica, roll back = restore the
pair". Linked from both deploying guides.

## Should-fix

### 6. A marketplace can never be corrected or removed (SCHEMA/API)

No `DELETE`/`PUT` for marketplaces exists; `guides/lifecycle-webhooks.md:42-44`
admits "there is no `DELETE /api/marketplaces/{name}`"; the estate reconciler is
additive-only (`config/SkillsGatewayProperties.java:596-598`); `url` has no
setter. `V1__init.sql:86` has `snapshots.marketplace_id REFERENCES marketplaces
(id)` with no `ON DELETE`. A typo'd URL or a moved upstream leaves a permanent
dead row the sync sweep keeps stamping.

### 7. `webhook_deliveries` grows without bound (SCHEMA)

Every delivery stores its full `payload TEXT` (`V1__init.sql:317-331`); there is
no `DELETE FROM webhook_deliveries` anywhere in `src/main/java`. The listing is
capped at 500 (`webhook/WebhookController.java:33-34`); the table is not. The
in-flight `bound-ledger-growth` change mentions neither this table nor
`vetting_runs`.

### 8. Four `V1` edits that are free today and migrations forever (SCHEMA)

- `vetting_runs.trigger TEXT` (`V1__init.sql:369`) holds a closed set the API
  already exposes as an enum (`ingestion`/`revet-scheduled`/`revet-manual`),
  against the file's own stated policy at lines 1-4.
- `marketplaces.name` (`:42`) has no `CHECK (name ~ '^[a-z0-9][a-z0-9_-]*$')`,
  yet `access_tokens.scopes` (`:252-255`) is comma-delimited *because* "names
  cannot contain the delimiter" — the schema does not enforce the assumption the
  token scoping relies on.
- No index on `access_tokens (principal)`, though `TokenRepository.java:126`
  filters on it for every token listing.
- `scopes`, `push_scopes`, `api_scopes`, `webhook_subscribers.events` are
  comma-delimited `TEXT` while `vetting_chain_orders.vetters` (`:602`) is
  `TEXT[]`.

### 9. Enum casing is inconsistent inside one document (API)

`openapi.json` carries `CLEAR`/`BLOCKED`, `PASS`/`WARN`/`FAIL`, `APPLIED`,
`GLOBAL`/`DEFAULT` beside `held`/`approved`, `admin`/`approver`, `append-only`,
`ingestion`. Renaming a value later is a break (`compatibility.md:202-203`).

### 10. Metrics can only leave by OTLP, and the chart cannot enable it (OPS)

`pom.xml` has no `micrometer-registry-prometheus`; `application.yaml` exposes
only `health,sbom`; `observability.md:104-112` says export needs
`arconia.otel.enabled=true` plus `OTEL_EXPORTER_OTLP_*`; `helm/values.yaml` has
no otel or prometheus values at all. The two metrics the docs say to **alert on**
— `storage.conditional_write.exhaustions` and `mirror.stale_refs`
(`observability.md:43,65`) — reach nobody on a default chart install.

### 11. Webhook signing secrets are plaintext at rest and undocumented (SECURITY/DOCS)

`webhook_subscribers.secret` and `marketplaces.webhook_secret`
(`V1__init.sql:67-70, 308-310`) are stored as-is; the only crypto in the tree is
`WebhookSigner` (HMAC). The docs state the PAT posture ("hashed at rest",
`reference/portal.md:828`) but say nothing about these. Recoverability is
legitimate — HMAC needs the key — so the gap is honesty, not design.

### 12. The two `RemovedProperties` refusals are "scheduled for removal at the next major" (API)

`compatibility.md:148-156` and `config/RemovedProperties.java`. The next major is
1.0.0, so shipping them freezes a migration aid for `roles.enabled` and
`cache.ref-freshness` into the supported surface.

### 13. The capability map's portal row is stale (DOCS)

`capability-map.md:33` says "The seven pages … overview, marketplaces,
marketplace detail, audit, adoption, tokens, webhooks." `api/SpaController.java:10`
routes eight, including `/vetting`, which `reference/portal.md:16` lists as a
governance page. The stop rule leans on this map; it should not under-count.

## What was checked and found sound

Do not re-spend effort here.

- **Schema quality overall is high.** Every timestamp `TIMESTAMPTZ`; closed sets
  are PostgreSQL enums with recorded rationale; invariants are `CHECK`s
  (`session_derived_credentials_hold_no_api_scope`, `machine_credentials_expire`,
  `a_revocation_is_never_reversed_by_…`, `UNIQUE NULLS NOT DISTINCT` where NULL
  means global); every sweep has a named partial index and a `sweep_leases` row
  rather than an advisory lock. Beyond #8, nothing to change.
- **`dev-insecure-auth` is gated as claimed.** `DevInsecureAuthGuard.java:57-63`
  refuses startup on any real OIDC signal; `RoleBootstrapGuard` refuses a gateway
  with no admin otherwise; the proxy-only blind spot is documented
  (`configuration.md:92`).
- **Facade, status and hook chains.** `/status/**` is PAT/IdP-bearer only,
  stateless, CSRF-off by design (`SecurityConfig.java:141-153`); `/hooks/**`
  verifies HMAC with `MessageDigest.isEqual` and caps the body
  (`InboundWebhookController.java:76-103`). Rate limiting is moot there — PATs are
  256-bit random looked up by SHA-256, the hook is HMAC-gated.
- **No secret reaches a log.** The only credential-adjacent `log.*` line is the
  issuer warning (`SecurityConfig.java:193`). One-time secrets appear only in
  `CreatedSink`, `CreatedSubscriber` and `SyncModeView`, matching the "returned
  exactly once" design.
- **Contract gates work as documented** — `openapi.json` equality test, oasdiff
  with raised severities, PR-title `!` requirement (`compatibility.md:232-268`).
- **Ledger export** is properly cursor-paginated and time-bounded
  (`FetchLogRepository.java:230`).
